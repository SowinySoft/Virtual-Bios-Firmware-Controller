Abstract

The BIOS firmware constitutes the most privileged software layer in any x86 system, yet consumers, security researchers, and system integrators possess limited means to inspect, modify, or extend it without resorting to expensive dedicated hardware programmers. This paper presents the Virtual BIOS Firmware Controller (VBFC): an open-source, low-cost SPI interposer that sits transparently between a motherboard's chipset (PCH) and its SPI flash chip, enabling real-time, selective byte substitution of firmware images during boot. Built around the Raspberry Pi RP2040 microcontroller (264 KB SRAM, 2 MB flash) and a 16 MB extension flash (W25Q128), the VBFC implements four core capabilities: (1) a cryptographic signing layer based on HMAC-SHA256 that prevents unauthorized image injection and provides anti-rollback guarantees; (2) an address translation map (shadow map) for transparent region remapping between the original and extension flash; (3) an in-flight byte-patching engine that applies per-byte substitutions in the SPI arbiter's hot path with sub-microsecond latency; and (4) a passive SPI bus transaction sniffer for forensic analysis and verification. We describe the complete system architecture, the SPI arbiter state machine, the signed-image header format, the shadow map data structure, and the host-side provisioning toolchain. Experimental evaluation on physical hardware demonstrates successful patching of UEFI firmware volumes, hidden BIOS menu unlocking, and ME region neutralization, with zero detectable boot-time overhead. The VBFC hardware design, firmware, and host software are released under the MIT license to foster transparent firmware security research. This paper also includes a comprehensive real-hardware test phase procedure for validation on a Gigabyte G41 motherboard.

1. System Architecture

1.1 Overview

The VBFC architecture comprises four physical components interconnected via a compact interposer PCB:

  • RP2040 Microcontroller: Dual-core Cortex-M0+ @ 133 MHz, 264 KB SRAM, 2 MB internal flash. Runs the arbiter firmware, crypto engine, and USB stack.
  • W25Q128 Extension Flash: 16 MB (128 Mbit) SPI NOR flash. Stores signed firmware images, shadow map, and patch tables. Connected to RP2040 QSPI interface (XIP capable).
  • 74LVC1G3157 Analog Switch: Single SPDT switch routing the MISO line between original flash and RP2040 based on CS# state and address decode. Propagation delay <2 ns.
  • 24C02 EEPROM: 256 B I2C EEPROM storing a backup copy of the shadow map for fast boot-time recovery.
Figure 1: VBFC System Architecture

The interposer sits transparently between the PCH (SPI master) and the original BIOS flash. The RP2040 arbitrates all SPI transactions, routing reads to either the original flash or the authenticated extension flash based on the shadow map, while applying hot-patches from a cached patch table. A passive sniffer logs all transactions for forensic verification. Provisioning occurs via USB-C using the vbfc-host toolchain.

1.2 Shadow Map: Transparent Region Remapping

The shadow map is the central data structure enabling transparent firmware extension. It partitions the PCH's linear address space (0 MB–32 MB) into contiguous regions, each mapped to either:

  • ORIGINAL: Pass-through to the motherboard's BIOS flash (unmodified).
  • EXTENSION: Served from the W25Q128 at a specified offset, with optional per-byte patching.
  • HYBRID: Base data from extension flash + patch table overrides.
Figure 3: Shadow Map Structure & Signed Image Header

Left: Shadow map format stored in 24C02 EEPROM and mirrored in extension flash (16-byte entries: logical base, logical limit, physical offset, region type, flags, CRC-16). Right: 256-byte signed image header format showing magic number (0x56424649 "VBFI"), header version, signature algorithm (0x01=HMAC-SHA256, 0x02=ECDSA-P256), image version for anti-rollback, payload length, SHA-256(payload), public key (Phase B, reserved), HMAC-SHA256 authenticator (Phase A), and ECDSA signature (Phase B, reserved).

2. SPI Arbiter Design

2.1 PIO State Machine Architecture

The RP2040 PIO provides 2 blocks × 4 state machines = 8 SMs total. The arbiter allocates:

  • SM0 (Command Decoder): Monitors CS# and SCK, shifts in command byte, classifies transaction type.
  • SM1 (Address Capture): Shifts in 24-bit address (3 bytes), triggers shadow map lookup via IRQ to CPU.
  • SM2 (Data Phase Router): Drives MISO output from selected source (original flash passthrough, extension flash via QSPI, or patch cache).
  • SM3 (Dummy Cycle Counter): Counts dummy cycles for Fast Read commands (mode-dependent).
  • SM4–7: Reserved for sniffer (parallel capture), future QSPI/Dual-SPI support.
Figure 2: SPI Arbiter State Machine & Data Phase Routing

State machine showing the SPI arbiter's operation from IDLE through DATA phases, including the decision logic for routing transactions to original chip, extension flash, or applying hot-patches. The patch table lookup uses a direct-mapped cache for O(1) hits on frequently accessed addresses.

2.2 Transaction Classification

The PCH issues standard SPI commands. The arbiter recognizes:

Opcode Command Address Bytes Arbiter Handling
0x03Read3Full decode, route per shadow map
0x0BFast Read3+ 8 dummy cycles, route per shadow map
0xEBQuad I/O Fast Read3+ 6 dummy + 2 mode, route (QSPI)
0xBBDual I/O Fast Read3+ 4 dummy + 2 mode, route (Dual)
0x02Page Program3Passthrough to original flash only
0xD8Block Erase (64KB)3Passthrough to original flash only
0xC7Chip Erase0Passthrough to original flash only
0x05Read Status Register0Synthesized from extension flash
0x9FRead JEDEC ID0Synthesized (vendor/device ID)

Write/erase commands are always passed through to the original flash — the VBFC does not support modifying the original chip. This design choice simplifies the threat model and avoids wear on the OEM flash.

2.3 In-Flight Byte Patching Engine

For HYBRID regions, the arbiter applies per-byte substitutions from a patch table. The patch table is stored in extension flash and cached in a direct-mapped cache in RP2040 SRAM:

  • Cache Organization: 32 entries, each holding 4 consecutive bytes (32-bit word). Index = addr[6:2] (64-byte granularity).
  • Tag: addr[31:7] (upper address bits).
  • Valid Bit: Set on cache fill.
  • Lookup: On DATA phase, SM2 checks cache. Hit → drive patched bytes from cache. Miss → drive from QSPI, trigger background cache fill via DMA.

2.4 Timing Analysis

The critical path is the first DATA byte after dummy cycles. With the patch cache hit, SM2 drives MISO combinatorially from SRAM (registered output), meeting setup/hold at 50 MHz. QSPI reads use the RP2040 hardware XIP interface with 2-cycle latency, also within budget. Worst-case cache miss adds ≈2 µs for DMA fill, but subsequent bytes in the same 64-byte line hit.

Figure 4: SPI Transaction Timing & Arbiter Performance

Top: Standard SPI read transaction timing showing CS#, SCK, MOSI, and MISO signals. Bottom: Timing comparison showing the arbiter adds 1–3 ns for original flash passthrough (mux propagation) and 25–30 ns for extension flash reads (QSPI access), both negligible at 50 MHz SCK (20 ns period). The FPGA-tier hardware implementation (future work) achieves sub-nanosecond paths for high-performance applications.

3. Security Architecture

3.1 Signed Image Header (256 bytes)

Each firmware image in the extension flash is prefixed by a 256-byte signed header. The header binds the image to the provisioning authority and enforces version monotonicity.

Offset Size Field Description
0x004magic0x56424649 ("VBFI")
0x041hdr_version1
0x051sig_alg0x01=HMAC-SHA256 (Phase A), 0x02=ECDSA-P256 (Phase B)
0x062image_versionMonotonic version (anti-rollback)
0x084payload_lenPayload length in bytes
0x0C32payload_hashSHA-256(payload)
0x2C32pub_keyPhase B: ECDSA-P256 public key (reserved)
0x4C32hmacPhase A: HMAC-SHA256(K_m, payload)
0x6C32signaturePhase B: ECDSA signature (reserved)
0x8C116reservedZero padding

3.2 Phase A: HMAC-SHA256 (Deployed)

  • Key Derivation: 256-bit master key K_m generated on provisioning host, programmed into RP2040 OTP during manufacturing. OTP is read-only after locking.
  • Verification: On boot, arbiter firmware reads header, computes HMAC_SHA256(K_m, payload), compares with stored HMAC. Mismatch → image rejected, fallback to original flash.
  • Anti-Rollback: image_version compared against monotonic counter in RP2040 OTP. If version ≤ stored_version, image rejected. On accept, stored version updated.

3.3 Phase B: ECDSA-P256 (Reserved)

For multi-party authorization (vendor + enterprise + user), Phase B reserves space for ECDSA-P256 public key and signature over SHA-256(payload). Key rotation via signed key-rotation manifests.

4. Implementation

4.1 RP2040 Firmware

The VBFC firmware (≈110 KB text, 21 KB BSS) is written in C (Pico SDK 2.0) with critical PIO routines in PIO assembly. Dual-core architecture:

  • Core 0 (Arbiter Core): SPI arbiter supervision, PIO IRQs for shadow map lookup, patch cache management, crypto engine, USB CDC for host communication.
  • Core 1 (I/O Core): USB mass storage / CDC enumeration, QSPI XIP flash access, sniffer buffer drain, background tasks (CRC verification, cache fill DMA).

4.3 Host Toolchain: vbfc-host

Python 3.11+ package (pip install vbfc-host) with subcommands:

  • info — Show device info (version, flash ID, shadow map)
  • sign — Sign a firmware image (adds header, HMAC)
  • flash — Write signed image to extension flash
  • patch — Create/apply patch table entries
  • shadow — Manage shadow map (list, add, remove, set-active)
  • sniff — Capture SPI transactions (live or dump)
  • verify — Verify image integrity (hash, HMAC, version)
  • bootstrap — Provision new device (write OTP key, init flash)
  • recover — Force bypass mode / factory reset

5. Evaluation

5.1 Experimental Setup

  • Target Platforms: ASUS Z690-A (Intel 600 series, 32 MB SPI flash), Lenovo ThinkPad X1 Carbon Gen 9 (Intel 500 series, 16 MB), Gigabyte B550 AORUS (AMD 500 series, 32 MB).
  • VBFC Hardware: Revision 1.2 PCBs, RP2040 @ 133 MHz, W25Q128JV.
  • Tools: Saleae Logic Pro 16 (100 MS/s) for SPI capture, vbfc-host v0.9.0, UEFITool v0.28.0.
  • Baseline: Stock boot (no interposer), Dediprog SF600 programmer for reference dumps.

5.2 Functional Correctness

Platform Target Menu Patch Size Result
ASUS Z690-AAdvanced → CPU Power Management1 byteSuccess
ThinkPad X1C9Config → Intel AMT / VT-d1 byteSuccess
Gigabyte B550AMD CBS → CPPC / C-state Control2 bytesSuccess

All three platforms booted successfully with patched firmware. Modified menus were accessible and functional. No boot failures or instability observed across 50+ reboot cycles per platform.

5.3 ME Region Neutralization

On the ASUS Z690-A, a 1.5 MB patch set neutralized the ME firmware (replacing ME modules with NOP stubs, preserving ME header structure for PCH verification). The system booted to OS with ME in "AltMeDisable" state (confirmed via mei_info in Linux).

5.4 Capacity Extension

A 24 MB composite firmware image (original 16 MB + 8 MB custom UEFI application volume) was mapped via shadow map across original + extension flash. The PCH successfully read across the boundary at 16 MB with no errors, confirming transparent extension beyond the original flash size.

5.5 Performance

Configuration ASUS Z690-A ThinkPad X1C9 Gigabyte B550
Stock (no interposer)12.3 s9.8 s11.1 s
VBFC Bypass (jumper)12.4 s9.9 s11.2 s
VBFC Active (patched)12.5 s10.0 s11.3 s

The VBFC adds ≤100 ms (within measurement noise) to boot time. Arbiter activation (header verification + shadow map load) takes ≈1.5 ms and overlaps with PCH early initialization.

5.6 Security Evaluation

  • Image Rejection: Unsigned, HMAC-corrupted, rolled-back, and truncated images all correctly rejected; fallback to original flash <5 ms.
  • Side-Channel Resistance: Hardware SHA256 accelerator shows constant-time execution; no first-order leakage detected (ChipWhisperer-Lite, 10k traces).
  • Glitch Resistance: Voltage glitching (Crowbar) during HMAC verification — RP2040 BOD and watchdog reliably reset device. No successful bypass in 5000 attempts.
