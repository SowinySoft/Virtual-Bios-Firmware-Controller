%--- Abstract ---
\begin{abstract}
The \ac{BIOS} firmware constitutes the most privileged software layer in any x86 system, yet consumers, security researchers, and system integrators possess limited means to inspect, modify, or extend it without resorting to expensive dedicated hardware programmers. This paper presents the \acf{vbfc} (\vbfc): an open-source, low-cost \ac{SPI} interposer that sits transparently between a motherboard's chipset (\ac{PCH}) and its \ac{SPI} flash chip, enabling real-time, selective byte substitution of firmware images during boot. Built around the \rp (\SI{264}{KB} \ac{SRAM}, \SI{2}{MB} flash) and a \wq 16 MB extension flash, the \vbfc implements four core capabilities: (1) a cryptographic signing layer based on \ac{HMAC}-\ac{SHA}256 that prevents unauthorized image injection and provides anti-rollback guarantees; (2) an address translation map (shadow map) for transparent region remapping between the original and extension flash; (3) an in-flight byte-patching engine that applies per-byte substitutions in the \ac{SPI} arbiter's hot path with \SI{<1}{\micro s} latency; and (4) a passive \ac{SPI} bus transaction sniffer for forensic analysis and verification. We describe the complete system architecture, the \ac{SPI} arbiter state machine, the signed-image header format, the shadow map data structure, and the host-side provisioning toolchain. Experimental evaluation on physical hardware demonstrates successful patching of \ac{UEFI} firmware volumes, hidden \ac{BIOS} menu unlocking, and \ac{ME} region neutralization, with zero detectable boot-time overhead. The \vbfc hardware design, firmware, and host software are released under the MIT license to foster transparent firmware security research. This paper also includes a comprehensive real-hardware test phase procedure for validation on a Gigabyte G41 motherboard.
\end{abstract}

\textbf{Keywords:} \ac{SPI}, \ac{BIOS}, firmware security, interposer, hardware root of trust, \ac{RP2040}, \ac{UEFI}, \ac{ME}, trusted computing, open-source hardware

\section*{Six Case Studies Addendum}
\addcontentsline{toc}{section}{Six Case Studies Addendum}

The VBFC platform has been extended through six independent case studies, each exploring a distinct aspect of firmware security and hardware evolution. All case studies are derived from independent Git branches that do not modify the core paper, ensuring complete isolation. Below is a summary of each case study.

\subsection{Case Study 1: FPGA SPI Arbiter}
\textbf{Purpose:} Explore an FPGA-based (Lattice ECP5 / Xilinx Artix-7) replacement for the RP2040 PIO arbiter to enable sub-nanosecond arbitration latency, full QSPI/OPI support, hardened crypto cores, multiple independent SPI channels, and formal verification of the arbiter state machine.

\textbf{Roadmap:} Define SPI arbiter FSM in Verilog $\rightarrow$ Simulate with ModelSim/Vivado $\rightarrow$ Synthesize on target FPGA $\rightarrow$ Integrate with RP2040/host toolchain bridge $\rightarrow$ Formal property checking (clock-domain crossing, safe states).

\textbf{Key Files:} scripts/vbfc_fpga_arbiter.v (Verilog FSM), scripts/tb_vbfc_spi_arbiter.v (testbench), scripts/property_checker.sv (SVA properties), docs/vbfc_fpga/integration.md (Wishbone bridge architecture).

\subsection{Case Study 2: ECDSA Key Rotation (Phase B)}
\textbf{Purpose:} Explore asymmetric key rotation (Phase B) to enable multi-party authorization (vendor + enterprise + user keys), key rotation without physical VBFC replacement (signed key manifests), and integration with certificate transparency logs for auditability.

\textbf{Roadmap:} Define ECDSA-P256 key manifest schema $\rightarrow$ Implement host-tool signing extension $\rightarrow$ Design secure OTP/element storage for Phase-B keys $\rightarrow$ Add key rotation workflow to vbfc-host CLI $\rightarrow$ Integrate with certificate transparency infrastructure.

\textbf{Key Files:} docs/vbfc_phaseb/README.md.

\subsection{Case Study 3: Remote Attestation}
\textbf{Purpose:} Extend the VBFC to produce signed attestation reports (via TPM-2.0 PCR measurements) to enable remote verification of device integrity.

\textbf{Roadmap:}
\begin{enumerate}
  \item Derive attestation key from RP2040 OTP master key
  \item Produce quote structure compatible with TCG TPM 2.0 or AMD SEV-SNP
  \item Include PCR measurements of firmware image + shadow map + patch table
  \item Integrate with remote verification services (e.g., Charter, Azure Attestation)
  \item Add CLI vbfc attest command for challenge-response
\end{enumerate}

\textbf{Key Files:} docs/vbfc_attestation/README.md.

\subsection{Case Study 4: Automated Patch Discovery}
\textbf{Purpose:} Integrate with firmware analysis frameworks (UEFITool, UEFIRE, IDA Pro plugins) to automatically identify patchable regions (hidden menus, feature flags, ME policy bits) and generate patch tables.

\textbf{Roadmap:}
\begin{enumerate}
  \item Define patch table format (offset, size, replacement bytes, authorization level)
  \item Build UEFITool plugin skeleton for VBFC region detection
  \item Outline UEFIRE rule-set for SPI flash post-IBB volume parsing
  \item Sketch IDA Pro Python plugin for auto-discovery of MMIO/register patches
  \item Conceptualize ``patch marketplace'': signed, community-contributed patches with reproducibility hashes
\end{enumerate}

\textbf{Key Files:} docs/vbfc_autopatch/README.md.

\subsection{Case Study 5: TPM/Measured Boot Integration}
\textbf{Purpose:} Extend VBFC to include PCR measurements (TPM 2.0 TPM2_Extend or IMA hooks) so the active firmware image and patch set are included in the measured-boot chain transparently.

\textbf{Roadmap:}
\begin{enumerate}
  \item Design PCR bank selection (e.g., PCR 0--7 or 12--15) for firmware image hash
  \item Implement vbfc tpm-extend command to extend selected PCR with SHA-256 of active image + patch table
  \item Add IMA appraisal hooks (on-board, if OS is Linux) for early-measurement reporting
  \item Produce measured-boot report format (EBR/EFI) compatible with UEFI firmware manager
  \item Integrate with platform firmware (TianoCore) to expose measured boot state to OS loader
\end{enumerate}

\textbf{Key Files:} docs/vbfc_tpm/README.md.

\subsection{Case Study 6: RP2350 Rev 2 Hardware Spec}
\textbf{Purpose:} Migrate the VBFC design from RP2040 to RP2350 (dual-core Arm Cortex-M33 @150 MHz + 2\ac{PIO}) to enable: 8-line Octal-SPI (OPI) support on a single MCU (eliminates need for external mux), USB 1.1 Full-Speed + Device + Host on the same die, 48+ GPIO (vs 26 on RP2040) for mux control, EEPROM, debug, and test points, and hardened crypto (hardware-accelerated CRC32, SHA-256, ECC M33).

\textbf{Hardware Spec:}
\begin{itemize}
  \item MCU: RP2350-A (replacing RP2040)
  \item 8-line SPI mux: TS3A5017 or equivalent (or connect OPI directly to flash)
  \item EEPROM: W25Q128 24C02 (unchanged) -- now accessed via dedicated GPIO lines
  \item USB: RP2350 D+/D- pins (same physical connectors)
  \item Power: Same 3.3\,V supply; add POR reset supervisor (e.g., TPS3825)
\end{itemize}

\textbf{GPIO Map (RP2350 vs RP2040):}
\begin{tabular}{lll}
  \textbf{Signal} & \rp2040 GPIO & \rp2350 GPIO & \textbf{Notes} \\
  SPI CS0 & 0 & 1 & \\
  SPI SCK & 1 & 2 & \\
  SPI MOSI & 2 & 3 & \\
  SPI MISO & 4 & 4 & \\
  MUX SEL & 5 & 5 & \\
  EEPROM WP & 6 & 6 & \\
  USB D+ & 24 & 7 & \\
  USB D- & 25 & 8 & \\
  DEBUG LED & 26 & 9 & \\
\end{tabular}

\textbf{Migration Roadmap:}
\begin{enumerate}
  \item Update RP2040 firmware (PIO $\rightarrow$ RP2350 PIO v2) -- same state machine, more pins available
  \item Update host-tool vbfc-host to map new GPIO offsets
  \item Update docs/vbfc_paper_full/sections_full/07_implementation.tex with revised pinout table
  \item Add docs/vbfc_rp2350_rev2/hardware_spec.md with full schematic notes
  \item Benchmark OPI read latency vs RP2040 QSPI (expected: 2--3$\times$ speedup)
\end{enumerate}

\textbf{Links:} RP2350 Datasheet: \url{https://www.raspberrypi.com/documentation/microcontrollers.html\#rp2350}.
